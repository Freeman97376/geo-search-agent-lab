# Query 拆分评估与真实平台偏差处理

日期：2026-09-28。状态：研究协议草案，尚未运行评估，也未确定验收阈值。

定量补充：[本地与真实平台的差距](platform_gap_evaluation.md)，定义引用概率误差、来源分布距离、自身波动参照、等价性判定与策略选择损失。

用户已明确要求该模块解决评估问题，并考虑复现与真实结果的偏差。本文暂将“真实结果”理解为目标平台在指定时间、接口与设置下的实际输出；目标仍是多个主流平台的引用趋势。真实平台输出是行为观测，不自动成为事实正确性的标准答案。

## 1. 三种评估分开记录

| 评估目标 | 参照物 | 通过能说明什么 | 不能说明什么 |
| --- | --- | --- | --- |
| 上游行为复现 | 锁定的 GPT Researcher 源码、同配置与记录的输入输出 | 包装、日志、Replay 是否保留了原有调用与数据流 | 已复制闭源平台的内部实现 |
| Query 拆分质量 | 人工标注的信息需求、条件、证据相关性 | 查询是否保留任务含义，是否带回有用证据 | 与某平台生成的查询相同 |
| 外部有效性 | 各真实平台的重复观测、独立验证集 | 本地结论在哪些平台、任务和时间范围内成立 | 永久通用的 GEO 效果或隐藏机制相同 |

复现原始模型配置与使用本地 Qwen 是不同实验配置。即使没有改 Agent 代码，换模型也可能改变规划；不能把两者的输出差异全部视为实现错误。

## 2. Query 拆分如何评分

### 评审材料

每题先标注：任务类型、实体、必要条件、证据需求列表、歧义和允许的合理解释。标注应先于查看候选 Planner 输出；允许多种有效拆法，不维护唯一正确 Query 字符串。无法从原问题消解的歧义单独标记，不强行奖励某一种猜测。

信息需求和检索表达需要分开。NIST TREC 的测试集合将主题、文档与相关性判断分开维护，并可汇集多个系统的候选文档供评审；本项目借用这一设计思路。[NIST：How To TREC](https://trec.nist.gov/howto.html)

### 第一版指标建议

| 指标 | 定义 / 记录方式 | 解释限制 |
| --- | --- | --- |
| 意图覆盖率 | 被至少一条 Query 充分表达的必要证据需求数 / 适用需求数 | 初版等权；部分覆盖单独标记，不任意给半分。无适用项记 N/A |
| 条件遗漏/冲突 | 逐项记录必要条件是否在适用的 Query 中遗漏、改变或矛盾 | 不要求每条 Query 都复制所有条件；严重冲突单独展示 |
| 无依据扩展 | 记录新增实体、结论前提及来源：用户、初搜、或无法追溯 | 来自初搜也不等于事实可信或符合任务，仍需相关性判断 |
| 重复程度 | 标出语义重复且没有新增检索价值的 Query 组 | 字符串相似度只作提示；不同语言或词汇可能有召回价值 |
| 格式与运行可靠性 | 原始响应可解析率、修复率、空响应、实际条数、重试/fallback、失败率 | 修复后成功与原始格式成功分别报告 |
| 证据覆盖率 | 实际取得且经判断有支持作用的文档覆盖了多少必要需求 | 区别于 Query 文本覆盖；抓取失败不算成功取得证据 |
| 增量检索收益 | 相对直接搜索原问题，新增了哪些已评审的有效证据和需求覆盖 | 同时报搜索次数、结果深度、耗时；多查几次的收益不能全归功于拆分 |

搜索比较使用相同服务、地区/语言、时间窗口、每次结果深度；Planner 方案之间尽量采用同一查询预算。原问题直搜可以作为低成本参照，但必须显式报告其预算差异。各方案结果联合去重后进行盲评，保留原始顺序与每条结果的 Query 来源。

开放互联网没有完整相关文档全集。若只标注汇集的候选池，只能报告候选池内的相对召回或证据覆盖；未评审文档保持 unknown，不冒充全网 Recall，也不能默认全部不相关。

### 谁来评分

- 程序检查：格式、条数、明确字段、延迟、次数和日志完整性。
- 人工评审：需求是否覆盖、条件是否变化、网页是否真的提供证据；隐藏方案名和模型身份，减少偏好影响。
- LLM 辅助：可提供逐项评分和可核对的文本依据；固定评审模型、提示与版本，先用人工样本校准，争议和严重错误人工复核。不能让生成模型的自评分充当唯一结论。

维护需求标注、评审依据和分歧记录；只有一名评审时如实标记，不能声称完成双人一致性验证。Agent 评估采用程序、模型及人工多种评分方式，并把多次尝试与完整运行记录分开保存，可参考 [Anthropic 的 Agent 评估实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。本文具体指标是项目提案，不是该文给出的标准。

## 3. 怎样对照真实平台

每个观测应包含 `platform / interface / reported_model / query_id / topic_group / locale / time_window / session_state / repeat_id`。不可控制或无法获得的字段记 unknown。网页产品与 API 分开；显式说明搜索是否实际触发，不将未搜索的回答混入搜索链路评估。

记录平台明确展示或接口实际返回的搜索 Query、来源、最终引用和答案。平台不公开的查询记 `unobserved`；不能根据引用反推唯一查询，也不能让模型事后猜测“自己搜过什么”当成执行日志。只显示部分查询时记 `partial`，不要按完整列表评分。

建议先做约 20–30 个独立问题、每题约 3 次的小规模试验来发现问题。这是工程起点，不是能证明引用概率或细微趋势的统计样本保证。正式样本量按先导波动、关心的最小效果和成本确定。

真实平台同题重复，与本地同题重复都要保存。时间、地区、会话和采样窗口尽量对齐，顺序交错以降低时间变化影响。分别报告：

1. 平台自身重复运行之间的变化范围；
2. 本地重复运行之间的变化范围；
3. 本地与该平台的差异及不确定性。

最终引用可以比较规范化 URL、域名集合、目标域名出现比例及来源类型分布。分别展示页面级与域名级差异；去追踪参数不能误删内容选择参数。集合重叠反映行为接近，不证明来源正确、信息相同或 Query 拆分相同。

失败率单列；“有效回答中的引用比例”和“所有尝试中成功产生目标引用的比例”分开命名并给出分母。平台限流、无搜索、引用字段缺失等情况不能默默删掉。

置信区间应考虑同题多次运行和同主题变体的相关性，不能把每条引用都当独立样本。先按题聚合重复运行，再采用适合设计的配对比较与主题组层面的区间估计；小样本时报告不确定，不强行宣布胜负。重复采样、聚类误差与配对比较的依据见 [Anthropic：评估的统计方法](https://www.anthropic.com/research/statistical-approach-to-model-evals)。

## 4. 有偏差时怎么处理

先保留原始运行和锁定的上游对照。根据下表定位，再创建单变量实验；不得为了匹配平台，把变更悄悄混入“原生复现”配置。

| 观察到的偏差 | 可做的定位实验 | 处理方式与边界 |
| --- | --- | --- |
| 查询措辞不同，需求及证据覆盖相当 | 盲评语义需求、条件与实际检索收益 | 记录为表达差异，不仅为凑字面一致而调 Prompt |
| 某类必要需求持续遗漏 | 固定初搜结果和模型比较规划 Prompt；再固定 Prompt 比较模型 | 分开改规划规则与模型，验证遗漏是否在新题上减少 |
| Query 合理但所需页面未召回 | 在本地用固定 Query 比较搜索服务/参数和候选结果 | 标为召回差异；换服务是独立配置。对平台隐藏检索原因只能保留假设 |
| 页面被召回，但正文缺失或关键信息未进入上下文 | 检查原始响应、抓取快照、过滤前后内容；用固定输入回放各步骤 | 区分抓取与过滤问题，不误归因于 Query 拆分 |
| 同一候选证据在本地能读取，但引用选择不同 | 固定本地上下文，仅比较回答模型或引用提示 | 可定位本地敏感环节；平台未公开上下文时不能声称找到其内部原因 |
| 差异与重复运行波动难区分 | 增加独立问题与必要重复，检查时间/缓存等共同因素 | 标为证据不足；“未发现显著差异”不等于已证明等价 |
| 本地改善，目标平台没有改善或方向相反 | 在未参与调参的题集与另一个时间窗口验证；确认两边比较的是同一变化 | 标为迁移失败/尚未验证；限制本地结论的适用范围 |
| 只有某平台或某类问题匹配 | 按平台、任务类型和语言分层报告 | 维护明确适用范围，不取平均掩盖方向相反的结果 |

相同最终结果可能来自不同中间路径；不同结果也不必然意味着 Query 模块失效。没有中间观测时，结论应停留在“行为差异”层面，不把本地消融推断直接当成闭源平台根因。

## 5. 防止只对样本调得像

将问题按主题/实体家族划分开发集和保留验证集，同题改写不能跨集合泄漏。开发集用于修改 Prompt 与参数；验证集用于检验这些修改，查看其结果后再调参则该集已成为开发数据，需要新的保留集。

初版不设一个“GEO 总分”或随意的“复现率 80%”。在正式验证前，确定主要指标、严重错误、可接受偏差范围和分层范围；必要时做等价性评估。单纯未检测到差异不能证明足够接近。

结果报告至少支持以下状态：

- **可控实验可用**：运行记录和快照足以复查，在本地可重放；质量水平单独报告。
- **特定范围外部验证通过**：在明确的平台/接口、问题类型和时间窗口满足预先指定的指标及偏差容忍度。
- **不确定 / 外部验证未通过**：样本不足、无法观察关键条件，或持久偏差超出容忍范围；报告具体失败切片。

这些是建议的报告状态，不是已实现的验收程序，也不是用户确认的阈值。

## 6. 未来 GEO 趋势验证的额外边界

Query 模块自身质量可以先评估，但它不能独自证明端到端引用趋势可迁移。

未来比较内容变化前后时，应同时报告本地效果和每个平台效果的方向、幅度与区间。基线引用分布接近只是必要的观察之一，不能推出平台对内容改动也会作相同反应。举例：本地引用率上升而平台稳定下降，在确认样本、时间和处理条件可比后，应判定该局部结论无法迁移，而不是将二者平均成小幅提升。

本地修改网页快照不会改变线上页面；在本地冻结 Query 时，线上平台也未必冻结 Query。只有目标平台能够实际接触可比的内容版本，并对索引/缓存/时间变化有记录和合理对照，才谈得上内容改动的外部验证。没有这些条件，只能报告自然观测中的相关趋势，不能声称因果提升。

当前交付是评估定义与偏差处理协议。下一步应先制作人工可审核的题目/需求标注样本和单独的 Planner 记录，再运行本地与平台小样本；尚未产生任何评估分数或平台复现结论。
